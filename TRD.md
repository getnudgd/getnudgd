| | |
|---|---|
| **Product** | GetNudgd (getnudgd.com) |

| **Owner** | Anmol (founder) |

Requirement IDs use the prefix `T-` and are referenced from `AGENTS.md` and the traceability matrix in section 12. Words **must**, **must not**, **should** carry their usual normative meaning.

---

## 1. System overview

GetNudgd is a modular monolith: one TypeScript codebase built into one Docker image, run as a `web` process (Next.js) and a `worker` process (job consumers) on a VPS, with all durable state in GCP managed services.

```
Internet ─▶ VPS (Docker Compose)                          GCP
            ├─ caddy      TLS, reverse proxy, headers     ├─ Cloud SQL PostgreSQL 16 (PITR, backups)
            ├─ web        Next.js standalone              ├─ Cloud Storage: gn-resumes, gn-proofs, gn-public
            ├─ worker     pg-boss consumers               ├─ Secret Manager
            ├─ gotenberg  DOCX → PDF                      ├─ Artifact Registry
            └─ cloud-sql-proxy (only if VPS is off-GCP)   ├─ Firebase Authentication
                                                          └─ Cloud Logging / Monitoring
External: Razorpay · WhatsApp Cloud API via BSP (Gupshup) · OpenAI · Brevo · gift-card vendor (stub)
```

## 5. Ledger requirements

| ID | Requirement |
|---|---|
| T-5.1 | Every business event that moves credits or points **must** create exactly one `ledger_txns` row with an `idempotency_key` derived from the event (`razorpay:{payment_id}`, `request:{id}:send`, `request:{id}:expire`, `request:{id}:tranche:1`). Re-posting an existing key **must** return the original transaction without side effects. |
| T-5.2 | Entries within a transaction **must** sum to zero per currency. This **must** be enforced in the `ledger` module and by a deferred constraint trigger in Postgres. |
| T-5.3 | Each request **must** have its own escrow account (`owner_type = escrow`, `owner_id = request_id`). |
| T-5.4 | Credit flows: purchase `platform → seeker`; send `seeker → escrow`; outcomes `escrow → platform` and/or `escrow → seeker` according to the request's `rules_version`. Points flows: `platform(points) → insider(points)` per tranche. The two currencies **must never** appear in the same transaction. |
| T-5.5 | Ledger writes **must** run in a database transaction that locks the affected accounts (`SELECT ... FOR UPDATE`) before reading balances. |
| T-5.6 | A Seeker's spendable balance **must** be computed from `ledger_balances`; the send operation **must** fail if balance < cost at lock time. |
| T-5.7 | A nightly `ledger.reconcile` job **must** recompute balances from entries, compare with the materialized view, and raise an alert on any difference. |
| T-5.8 | Admin credit grants **must** post `platform → seeker` with reason and audit entry; no other path may create credits outside payments and refunds. |

## 6. Request lifecycle requirements

### 6.1 States and transitions

| From | Event | To | Side effects |
|---|---|---|---|
| — | `send` | SENT | escrow credits; schedule `request.expire` at `respond_by`; notify Insider |
| SENT | `accept` | ACCEPTED | notify Seeker; cancel expire job |
| SENT | `decline` | DECLINED | refund per rules (decline before review); notify Seeker; update Insider response rate |
| SENT | `expire` (timer) | EXPIRED | refund per rules (expiry); notify both; lower Insider response rate |
| SENT | `cancel` (Seeker) | CANCELLED | full refund; notify Insider |
| ACCEPTED | `submitProof` | PROOF_PENDING | notify Admin queue |
| ACCEPTED | `declineAfterReview` | DECLINED | refund per rules (decline after review); notify Seeker |
| PROOF_PENDING | `verifyProof` (Admin) | SUBMITTED | release tranche 1; schedule `request.windowClose` at `window_deadline`; notify both |
| PROOF_PENDING | `rejectProof` (Admin) | ACCEPTED | notify Insider with reason; one re-upload allowed |
| SUBMITTED | `reportInterview` (either) | INTERVIEW_REPORTED | set `dispute_deadline`; notify other party |
| INTERVIEW_REPORTED | `dispute` (other party) | DISPUTED | notify Admin |
| INTERVIEW_REPORTED | dispute window elapses | INTERVIEW | release tranche 2; notify both |
| DISPUTED | `resolve` (Admin: interview) | INTERVIEW | release tranche 2 |
| DISPUTED | `resolve` (Admin: no interview) | NO_INTERVIEW | refund per rules (no interview) |
| SUBMITTED | `windowClose` (timer) | NO_INTERVIEW | refund per rules (no interview); Insider keeps tranche 1; notify both |
| INTERVIEW | — | COMPLETE | terminal |
| NO_INTERVIEW | — | CLOSED | terminal |

### 6.2 Rules

| ID | Requirement |
|---|---|
| T-6.1 | The transition table **must** be the single source of truth in `src/modules/requests/state.ts`; any event not listed for the current state **must** be rejected with a problem-details error. |
| T-6.2 | Every transition **must** write a `request_events` row and any ledger transaction in the same database transaction. Notifications and timers **must** be enqueued after commit. |
| T-6.3 | Each request **must** store `rules_version` at creation; refund and tranche calculations **must** use that version. |
| T-6.4 | Timer jobs **must** re-read the current state and act only if the expected state still holds. |
| T-6.5 | An hourly `requests.sweep` job **must** find requests whose deadline passed without a transition and apply the timer transition. |
| T-6.6 | Weekly cap: `send` **must** fail if the Insider's `weekly_used >= weekly_limit`, `is_available = false`, or `reverify_due_at < now()`. |
| T-6.7 | Insider response rate **must** be recomputed on each terminal transition from SENT. |

| `request.disputeClose` | reportInterview | `request:{id}:dispute` | 8 | delayed to `dispute_deadline` |
| `insider.reverify` | verified | `insider:{id}:reverify` | 8 | reminder at T-7d; hide at T |
| `insider.weeklyReset` | cron weekly | singleton | 1 | reset `weekly_used` |
| `notify.send` | any transition | `notify:{id}` | 8 | channel choice, retry with backoff, email fallback after 15 min |

| `payments.reconcile` | cron nightly | singleton | 1 | compare with Razorpay API; credit missed payments |
| `ledger.reconcile` | cron nightly | singleton | 1 | drift check and alert |
| `requests.sweep` | cron hourly | singleton | 1 | apply missed timer transitions |
| `whatsapp.inbound` | webhook | `wa:{message_id}` | 4 | session state machine, media download |
| `flags.scan` | cron nightly | singleton | 1 | duplicate pairs, shared devices, velocity |

| ID | Requirement |
|---|---|
| T-8.1 | Every job **must** be idempotent and re-check current state before acting. |
| T-8.2 | Jobs **must not** call other jobs synchronously; they enqueue. |
| T-8.3 | Failed jobs **must** retry with exponential backoff (max 5 attempts) and then land in a dead-letter view visible at `/admin/jobs`. |
| T-8.4 | The worker **must** expose liveness via a heartbeat row updated every 30 seconds; the health endpoint **must** report the worker unhealthy after 120 seconds without a heartbeat. |

## 10. Security and privacy requirements

| ID | Requirement |
|---|---|
| T-10.1 | Secrets **must** be stored in GCP Secret Manager and materialised on the VPS as a root-owned `.env` with mode 0600, or read at boot via the Secret Manager SDK. Secrets **must never** be committed, logged, or placed in `NEXT_PUBLIC_` variables. |
| T-10.2 | Caddy **must** set HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a Content-Security-Policy that allows only self, Firebase, Razorpay checkout, and Google Fonts, and **must** restrict `/admin*` to `ADMIN_IP_ALLOWLIST`. |
| T-10.3 | Server actions **must** be protected by Next.js origin checks; public forms (waitlist, survey) **must** include a honeypot field and rate limiting. |
| T-10.4 | Session cookies **must** be HttpOnly, Secure, SameSite=Lax, signed with `SESSION_COOKIE_SECRET`, rotated on privilege change, and revocable by user id. |
| T-10.5 | Work-email OTP codes **must** be 6 digits, hashed at rest, expire in 10 minutes, allow 5 attempts, and be rate limited to 3 sends per hour per user. |
| T-10.6 | All database access from the application **must** use a role without DDL rights and without UPDATE/DELETE on append-only tables. |
| T-10.7 | Logs **must not** contain resume text, proof content, phone numbers in full, OTP codes, tokens, or PAN. |
| T-10.8 | Cloud SQL **must** require SSL and accept connections only from the VPC (GCE VPS) or from the proxy service account (external VPS). |
| T-10.9 | Uploads **must** be validated by magic bytes, not only extension, and scanned for macros (DOCX with `vbaProject.bin` rejected). |
| T-10.10 | Deletion (PRD R17) **must** complete within 24 hours and be logged in `admin_audit_log` with the anonymised id. |

## 18. Definition of done (technical)

A requirement is done when: its tests exist and pass in CI; the code respects T-3.x structure rules; no business literal is present; idempotency keys cover every side effect; problem-details errors are used; migrations are generated and applied on staging; the feature is verified on staging with output attached to the task report; and the traceability matrix row is updated if scope changed.
